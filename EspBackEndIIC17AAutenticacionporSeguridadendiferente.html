Securitización de aplicaciones web de servidor

Para estos casos debemos crear un cliente confidencial en Keycloak. Como no se genera un código de autorización, no existe la posibilidad de que un atacante se interponga en el medio. Como vimos, tendremos que agregar también una URL de dirección (open redirect) para asegurarnos de que el usuario está trabajando en un sitio seguro y evitar que un tercero quiera manipular la redirección. En el caso de que lo intente, se redireccionará de todas formas a la URL preconfigurada. Ejemplo: 

    
      //trusted-site.com/...?redirect_uri=https://attacker.com

Securitización de SPA con API REST dedicada

Una SPA con una API REST dedicada en el mismo dominio debe ser securitizada en Keycloack de la misma forma que una aplicación de back end web.

Por lo tanto, esta aplicación debe delegar el flujo de código de autorización a la API REST que invoca y utilizar sesiones HTTP para hacer segura la integración entre el front end y el back end.

Securitización de una SPA con una API REST como intermediaria

La forma más segura de invocar una API REST externa desde una SPA es con una API intermedia desplegada en el mismo dominio de la SPA, delegando la gestión del cliente confidencial hacia nuestro IAM y gestión de tokens de “forma invisible” para el web browser, minimizando la posibilidad de alteración de tokens de refresh.

Esta arquitectura se llama Back end for Front end (BFF) y trata de hacer más portable la SPA, orientando la misma a la vista y su comportamiento, desligándose de lo referido a la lógica propia de la aplicación. La lógica la delega a una API intermediaria que terminará invocando a los servicios finales de negocio, por ejemplo, la imputación de un pago con tarjeta de crédito al microservicio de tarjetas.

Otra ventaja clara de esta solución es que no tendremos que lidiar o configurar CORS (cross-origin resource sharing) dado que la API intermedia está en el mismo dominio. En caso de que no lo fuese, deberíamos gestionar el permiso adecuado para poder llamar APIs de diferente dominio desde la SPA de origen.

Securitización de una SPA con una API REST externa

Para este tipo de arquitectura tendremos que implementar el flujo de autorización directamente en la SPA con un cliente público configurado en Keycloak, en lugar de un cliente privado que utilice secrets. Esto claramente es la solución más insegura al tener todo expuesto en el navegador web. No obstante, existen diferentes técnicas que minimizan el riesgo de corrupción del flujo de autorización:

  • Tener tokens de refresco con expiración corta (por ejemplo, 30 minutos), configurándose en Keycloak desde los timeouts de sesión para el cliente público.
  • Rotar los tokens de refresco, habilitando la opción Revoke Refresh Token dentro del realm que tiene como consecuencia eliminar el uso de un token de refresco que ya fue utilizado. La sesión se invalida en caso de usarse.
  • Utilizar PCKE.
  • Evitar el uso de variables de guardado de datos en HTML5 que sean predecibles para obtener el token, por ejemplo: window.sessionStorage.accessToken.
  • Proteger la SPA contra ataques cross-site scripting (XSS) y otros ataques según las mejores prácticas de Open Web Application Security Project (OWASP).

Securitización de API REST y servicios

Cuando un servicio API REST tiene invocar otra API REST protegida por Keycloak, primero tiene que obtener un access token para luego incluirlo en el authorization header del request
Authorization: bearer eyJhbGciOiJSUzI1NiIsInR5c…

La API receptora valida este token y decide qué hacer según el permiso que le fue otorgado en la configuración del IAM.

En este ejemplo se ve cómo la aplicación llama al servicio A con un access token, y este llama a los servicios B y C con el mismo token de acceso.

Para obtener este comportamiento podemos definir el uso de cuentas de servicio en la configuración de un cliente en Keycloak, permitiendo a un servicio de terceros obtener un token en representación del cliente. Para esto se debe realizar la siguiente configuración:

  • Client ID: service
  • Client Protocol: openid-connect
  • Access Type: confidential
  • Standard Flow Enabled: OFF
  • Implicit Flow Enabled: OFF
  • Direct Access Grants Enabled: OFF
  • Service Accounts Enabled: ON

Dado que la opción Standard Flow Enabled fue desactivada, no podemos obtener tokens usando el flujo del código de autorización. Sin embargo, como Service Accounts Enabled fue activado, podemos utilizar el flujo de credenciales de cliente que nos permite obtener tokens en representación de un tercero utilizando los siguientes parámetros en la petición HTTP:

  • client_id
  • client_secret
  • grant_type=client_credentials

Para esta prueba podemos usar nuestra terminal y guardar en una variable de entorno el secret generado en Keycloak para el nuevo cliente: 

    
      $ export SECRET=

Luego podemos invocar a la URL de generación de token indicando el secret y los parámetros de flujo de cuenta de servicio: 

    
      curl --data "client_id=service&client_secret=$SECRET&grant_type=client_credentials" http://localhost:8080/auth/realms/myrealm/protocol/openid-connect/token

Obteniendo como resultado el token final:

    
      {
        "access_token": "eyJhbGciOiJSUzI1NiIsI…",
        "expires_in": 299,
        "token_type": "bearer",
        "scope": "profile email",
      }
